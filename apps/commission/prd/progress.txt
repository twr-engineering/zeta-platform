CACHING DECISION (the §3.5/NFR "cached, invalidated by basis_version" line — measured &
decided per the brief): COMPUTE-ON-READ, no cache. Two tiny indexed parallel reads

here a cache is not just unnecessary but WORSE for a versioned contract: basis_version must
be read live (it IS the coherence token), so a cache over the cells could serve M3 a NEW
version with OLD numbers on any missed invalidation — the worst failure for a cache token.
Reading both live keeps version+numbers consistent by construction.

## Rate limiting / hardening — native vs added (M0 §8, FR of M0.4 hardening pass)
  What Supabase/GoTrue provides NATIVELY (server-side, not something we implement):
    - Auth endpoints are rate-limited by GoTrue: sign-in / sign-up / token refresh / OTP /
      password-recovery / verify all have per-IP and per-window limits (configurable in the
      dashboard). Email sending is separately rate-limited (this is M0.1's SMTP blocker).
    - Passwords are bcrypt-hashed by GoTrue; sessions are JWT + rotating refresh tokens.
  What M0.4 ADDED:
    - Session invalidation on password change (global signOut) — the §8 requirement.
    - Current-password re-authentication before password AND email change, which also means
      those actions ride GoTrue's rate-limited signInWithPassword rather than being an
      unthrottled side door.
    - Security response headers (next.config.ts headers()): X-Frame-Options DENY,
      X-Content-Type-Options nosniff, Referrer-Policy strict-origin-when-cross-origin,
      Permissions-Policy (camera/mic/geo/topics off), HSTS (inert on localhost, live on
      Vercel), and a CSP of frame-ancestors 'none' / base-uri 'self' / object-src 'none' /
      form-action 'self'. Deliberately NO default-src or script/style CSP: default-src would
      fall through to connect-src and block the browser Supabase client + Next HMR socket, and
      a nonce-based script CSP is a documented follow-up (see gaps).
    - Deletion is service-role + typed-confirmation + own-id-only; the whole-workspace export
      and every account read are RLS-scoped with no id in any URL.

## CRITICAL finding from live verification — PostgREST returns numeric as FLOAT
`select("*")` on tax_settings returned `ewt_rate: 0.1` (a JSON number -> IEEE-754 double)
and even dropped scale (`3600000`, not `3600000.00`). That is a binary float in a money
path, which Master PRD §4.3 forbids outright, and `supabase gen types` types these columns
`number`, baking the mistake into the types.
Fix (in place, verified live):
- Money/rate columns are selected with a `::text` cast -> "0.1000" / "3600000.00", exact
  and scale-preserved. Selects live in src/lib/supabase/selects.ts. NEVER `select("*")` on
  a table carrying money.
- Types are layered so regeneration cannot silently reintroduce the float:
    src/types/database.generated.ts  machine-generated, do not edit
    src/types/database.ts           money-safe override (numeric -> string), audit Update: never
    src/types/entities.ts           named row aliases
  A tsc assertion confirmed a float rate fails to typecheck.
- End-to-end: rates fetched from the LIVE db reproduce the PRD's ₱50,000 Inclusive split
  (GCI 44,642.86 / EWT 4,464.29) exactly.
M1/M4/M5 MUST add their `::text` selects + overrides when they add money tables.
